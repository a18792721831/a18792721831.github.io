## 1\. 介绍

defer 语句用于延迟函数的调用，常用于关闭文件描述符、释放锁等资源释放场景。  
defer 语句采用后进先出的设计，类似于栈的方式，函数执行时，每遇到一个defer都会把一个函数  
压入栈中，函数返回前在将函数从栈中取出执行，最早被压入栈中的函数最晚被执行。  
不仅函数正常返回会执行被defer延迟的函数，函数中任意一个return语句、panic语句均会触发延迟函数。

## 2\. 特点

### 2.1 使用限制

defer 不仅可以用于资源释放，也可以用于流程控制和异常处理，但defer关键字只能作用域函数或函数调用。

#### 释放资源
    
    
    func TestTwo(t *testing.T) {
    	lock := sync.Mutex{}
    	lock.Lock()
    	defer lock.Unlock()
    }
    

defer 常用于关闭文件句柄、数据库连接、停止定时器Ticker及关闭管道等资源清理场景。

#### 流程控制
    
    
    func TestThree(t *testing.T) {
    	wg := sync.WaitGroup{}
    	defer wg.Wait()
    }
    

defer也可用于控制函数执行顺序，比如配合wait.Group实现等待协程退出。

#### 异常处理
    
    
    func TestFour(t *testing.T) {
    	defer func() {
    		if err := recover(); err != nil {
    			fmt.Println(err)
    		}
    	}()
    }
    

defer也常用于处理异常，与recover配合使用可以消除panic，另外，recover只能用于defer函数中。

### 2.2 行为规则

#### 延迟函数的参数在defer语句出现时就已经确定

比如如下例子：
    
    
    func TestFive(t *testing.T) {
    	i := 1
    	defer fmt.Println(i)
    	i++
    }
    

defer语句中的fmt.Println参数i值在defer出现时就已经确定了，实际上是复制了一份。  
后面对变量i的修改不会影响fmt.Println函数的执行，仍然打印1.  
![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/470263a0879b4e879fb1832dbb178835.png#pic_center)

> 如果参数是指针，那么传入的是地址，defer后面对指针的值的变化，在defer中仍然能感知到。
    
    
    func TestFive(t *testing.T) {
    	i := 1
    	i_p := &i
    	defer fmt.Println(i)
    	defer func() {
    		xxx := *i_p
    		fmt.Println(xxx)
    	}()
    	i++
    	*i_p++
    }
    

![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/533d72a6fd4c48edab881067b10fc77a.png#pic_center)

#### 延迟函数按后进先出(LIFO)的顺序执行，先出现的defer后执行

定义defer类似于入栈操作，执行defer类似于出栈操作。  
设计defer的初衷是简化函数返回时资源清理的动作，资源往往有依赖顺序，比如先申请A资源，  
在根据A资源申请B资源，根据B资源申请C资源，即申请顺序是A->B->C，释放资源时需要反向进行。

> 每次申请到一个用完需要释放的资源时，立即定义一个defer来释放资源时一个很好的习惯。

#### 延迟函数可能操作主函数的具名返回值

定义defer的函数可能有返回值，返回值可能有名字(具名返回值)，也可能没有名字(匿名返回值)，延迟函数可能会影响返回值。

**函数返回过程**  
关键字return不是一个原子操作，实际上return只代表汇编指令ret，即跳转程序执行。  
比如语句return i，实际上分两步执行，即先将i值存入栈中作为返回值，然后执行跳转，  
而defer的执行正是在跳转前。  
也就是说defer执行时还是有机会操作返回值的。  
**具名返回值**
    
    
    func TestSix(t *testing.T) {
    	fmt.Println(add())
    }
    
    func add() (res int) {
    	i := 1
    	defer func() {
    		res++
    	}()
    	return i
    }
    

![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/555e333d05cb44008f2915cc435196b4.png#pic_center)

> 相当于直接操作具名返回值。  
>  return i 实际上等价于 res = i , goto 跳转  
>  defer 相当于在 上面两句中间插入了一句res++  
>  如果defer中是对i++，那么i相当于是作为闭包参数拷贝到了defer函数中，只是一个值传递行为。  
>  而且不会修改res的值。

**返回字面值**  
不管是具名返回值，还是匿名返回值，如果返回字面量，那么defer都无法操作的。  
假设 return 3,是将字面量压入栈，然后跳转的。defer语句不管如何修改，都无法修改压入栈的字面量。  
**匿名返回值**  
匿名返回值可以理解为用一个临时变量存储返回值，然后将临时变量压入栈，接着跳转。  
所以defer可以引用返回值变量，但是因为在压入栈的时候，已经做了变量拷贝，在defer中使用变量，相当于是值传递了  
(如果是引用的话，除非返回的也是引用，这样就是多个变量引用了同一个地址，相当于函数调用的引用传递了，那么defer的修改也是生效的)

## 3\. 原理

### 3.1 数据结构

在`src/runtime/runtime2.go`中定义了defer的数据结构
    
    
    // _defer保存了延迟呼叫列表中的一个条目。
    // 如果在此处添加字段，请在freedefer中添加代码以清除它。
    // 此结构必须与cmd/compile/internal/gc/reflect中的代码匹配。go：defestact
    // cmd/compile/internal/gc/ssa.go:（*state）.调用。
    // 一些延迟将在堆栈上分配，一些在堆上分配。
    // 所有延迟在逻辑上都是堆栈的一部分，因此写入障碍
    // 不需要初始化它们。所有延期必须手动扫描，
    // 对于堆延迟，标记为。
    type _defer struct {
    	siz     int32 //包括参数和结果
    	started bool
    	heap    bool
    	sp      uintptr // 函数栈指针
    	pc      uintptr // 程序计数器
    	fn      *funcval
    	_panic  *_panic // 正在蔓延的恐慌推迟了
    	link    *_defer // 链接多个defer
    }
    

每个_defer实例都是对一个函数的封装，它拥有执行函数的必要信息，比如栈地址，程序计数器，函数地址等等。  
实际上，编译器会把每个延迟函数编译成一个_defer实例暂存到goroutine数据结构中，待函数结束时在逐个取出执行。  
每个defer语句对应一个_defer实例，多个实例使用指针link链接起来形成一个单链表，保存到goroutine数据结构中。

### 3.2 defer入栈

每次插入_defer实例时，采用头插法加入链表  
![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/4fcc87dd6b3a4c999122ca06ce67a126.png#pic_center)

gp是goroutine拿到p后的变量，gp._defer每次都会设置为d,而d则是新加入的_defer.  
在函数返回跳转前，从gp._defer中依次取出执行。  
实现了先进后出的栈结构。

> 这里有个小知识，如果用链表实现栈和队列的结构，假设是单链表，那么头插法表示栈，尾插法表示队列。(假设都用链表头表示链表)

一个goroutine可能连续调用多个函数，defer的添加过程跟上述流程一致，进入函数时添加defer，离开函数时取出defer，所以即便调用多个函数，  
也总是能保证defer是按LIFO方式执行的。

## 4\. 总结

  * defer 定义的延迟函数参数在defer语句出现时就已经确定了
  * defer 定义的顺序与实际的执行顺序相反
  * return 不是原子操作，执行过程是：保存返回值(如果有) -> 执行defer(如果有) -> 执行跳转
  * 申请资源后立即使用 defer 关闭资源是一个好习惯

## 5\. 性能优化

defer 的实现机制在Go的演进过程中不断被优化，根据实现机制的不同，可以把defer分为三种类型。

  * heap-allocated: 存储在堆上的defer， Go 1.13 之前只有这种类型
  * stack-allocated: 存储在栈上的defer, Go 1.13 引入这种类型
  * open-coded: 开放编码类型的defer，Go 1.14引入这种类型

上面看的是第一种类型，存储在对上的defer，所以在deferreturn中执行的时候，会有一个操作是释放_defer实例。  
在G0 1.13及Go 1.14引入新的类型后，原来的类型也没有被废弃，而是多种类型共存，编译器会决策使用何种类型。  
优先使用open-coded，stack-allocated次之，在有些编译器无法决定的场景或受限的场景中则会使用heap-allocated。  
在deferproc,deferprocStack,deferreturn中都有如下代码  
![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/60cabe929e8d4d74864f74e0ba2e9afb.png#pic_center)

如果是 open-coded，那么什么都不干，如果是stack-allocated，那么需要处理参数，默认是heap-allocated。

### 5.1 heap-allocated

编译器将defer语句编译成一个deferproc函数调用，然后运行时执行deferproc函数。  
deferproc函数会根据defer语句生成一个_defer实例并插入goroutine的_defer的链表头部。  
同时编译器还会再函数尾部插入deferreturn函数，deferreturn函数会逐个取出_defer实例并执行。  
![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/857f18de46114c9a9ff35df5f08496ff.png#pic_center)

### 5.2 stack-allocated

栈defer正式为了提高堆defer的内存使用效率而引入的，编译器将defer语句编译成一个deferprocStack函数调用。  
![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/5730438994ab4f1fbefc7639929e519f.png#pic_center)

stack-allocated与heap-allocated最大的不同就是_defer.heap = false  
deferprocStack的工作机制与deferproc类似，区别在于编译器会直接在栈上预留_defer的存储空间，deferprocStack不需要在分配空间。  
deferprocStack仍然需要将_defer插入协程g的_defer链表中。  
在函数结尾处，编译器仍然会插入deferreturn函数，不管是那种defer，最终执行的都是deferreturn，在deferreturn中，调用释放_defer实例。  
![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/e8b204e92cfc42768536e8568a940e2c.png#pic_center)

如果是heap-allocated，那么_defer.heap=true,就会执行后面的释放操作。  
如果是stack-allocated，那么_defer.heap=false，就会直接return，不会在执行后续释放操作。  
编译器会尽可能地把derer语句编译成栈类型，但由于栈空间有限，并不能把所有的defer都存储在栈中，所以还需要保留heap-allocated .

> 在Go 1.13 中引入栈defer，在Go 1.13 的Release Notes 中，官方声称性能提升了近 30%

### 5.3 open-coded

无论heap-allocated还是stack-allocated的defer，编译器只能把defer替换成相应的函数，对于heap-allocated而言，  
是deferproc函数，对于 stack-allocated而言，则是deferprocStack函数，只能由运行时调用这些函数，然后创建_defer节点并存储，  
最后通过deferreturn函数取出_defer节点在执行。  
如果编译器能把defer语句直接翻译成相应的执行代码并插入函数尾部，那么就会节省_defer节点转储的代价。事实上，open-coded就是采用这种机制。  
open-coded的defer没有deferproc，deferprocStack，也没有deferreturn，延迟函数被直接插入函数尾部，这样一来，延迟函数的调用将变得跟普通函数调用一样高效。  
open-coded与heap-allocated和stack-allocated最显著的区别是编译器完成了defer语句的预处理，运行时不需要参与预处理defer，只需要执行就行了。  
但是并不是所有的defer语句都可以被编译器处理成open-coded类型。

  * 编译时禁用了编译器优化，`-gcflags=“-N -l”
  * defer出现在循环语句中
  * 单个函数中，defer出现了8个以上，或者return语句的个数和defer语句的个数乘积超过了15

> Go 1.14 的Release Notes 中，官方声称大多数场景下defer的性能已经跟直接的函数调用不相上下了，因此defer可以被应用到对性能格外挑剔的场景中了。

#### 禁用编译器优化

由于编译器在编译时决定了defer的类型，对于开放编码而言还需要在用户的函数体中插入执行代码，属于编译优化的一种，所以如果编译项目时  
禁用了编译优化，那么编译器不会把defer选择为open-coded类型

#### 循环语句

如果defer语句出现在循环体中，那么编译器在编译阶段无法确定最终将生成多少个defer，也就无法再函数尾部插入代码，所以不能把defer处理成open-coded

#### 限制 defer 数量

在编译器将defer语句编译成open-coded时，单个函数内的defer语句越多，编译器实现越复杂。支持无限的defer语句是不现实的，最终必须在  
设计复杂度和实际场景之间做权衡和取舍。
    
    
    func add() (res int) {
    	var b bool
    	if b {
    		defer fmt.Println(b)
    	}
    	return 1
    }
    

对于上面的代码中，编译的时候，因为无法确定b的值，所以很难确定defer是否需要执行。  
实际上尽管编译器无法再编译阶段确定判断条件是否成立，但还是会把上面的defer语句插入函数尾部，  
复杂的是运行时需要有手段来根据条件判断成立与否来决定是否要执行编译插入的代码。  
为此，Go 引入了deferBits，即编译器在函数内创建一个字节(8bit)的变量，并在函数中插入相应代码，确保运行时，  
每经过一个defer语句(说明defer被触发)，就把deferBits相应位置置为1。那么在函数尾部，运行时就可以根据deferBits相应位的值来决定要不要执行插入的代码。

> 这个设计非常巧妙，在函数开始的时候，创建一个8bit的变量，当运行的时候，经过了defer,就把这个defer的触发标志设置为1，在结束的时候，根据是否触发决定是否执行。

因为deferBit的长度为一个字节，也就是8bit，这就是为什么单个函数defer的数量被限制在8个以下的原因。  
![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/d41ae06ce736419ca155351f6d2ea816.png#pic_center)

在编译器中没如果单个函数中defer的数量超过8，则直接对该函数禁用open-coded。  
![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/edc8a2b59e3f471cb1eed4529bd2fb1d.png#pic_center)

另外如果函数中return语句的个数和defer语句的个数乘积超过了15，也直接禁用open-coded.  
![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/5964b73d63f64d17b95e086a41d60525.png#pic_center)

如果函数出口越多，则函数defer的数量越多，编译器实现起来就越复杂，不管是数字8还是15，都是权衡的结果。

> 如果函数中超过8个defer，那么所有的defer都不会被处理成open-coded，而不是前8个还是open-coded，其余的是heap-allocated或stack-allocated。  
>  如果函数中年的return语句的个数和defer语句的个数的乘积超过15，那么所有的defer也都不会处理成open-coded  
>  编译器只能处理包含少量的defer，对于大量的defer，由于处理复杂度急剧上升而不得不放弃，最终采用heap-allocated或stack-allocated
> 
> 数量的限制也可用于来指导开发：
>
