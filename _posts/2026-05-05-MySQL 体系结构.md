#### 连接层

连接层是 MySQL 的最上层，主要负责客户端连接的管理和认证。

**主要职责：**

  1. **连接管理** ：负责监听客户端的连接请求，为每个连接创建一个线程（或从线程池中分配）
  2. **认证授权** ：验证客户端的用户名、密码，检查客户端的访问权限
  3. **连接池管理** ：维护连接池，复用连接，减少连接创建的开销
  4. **SSL/TLS** ：支持加密连接，保证数据传输安全



**连接相关参数：**

```sql
-- 查看最大连接数
SHOW VARIABLES LIKE 'max_connections';

-- 查看当前连接数
SHOW STATUS LIKE 'Threads_connected';

-- 查看连接超时时间
SHOW VARIABLES LIKE 'wait_timeout';
SHOW VARIABLES LIKE 'interactive_timeout';

```

**线程模型：**

从 MySQL 5.6 开始，引入了线程池（Thread Pool）插件，可以复用线程，减少线程创建和销毁的开销。

```sql
SHOW VARIABLES LIKE 'wait_timeout';
SHOW VARIABLES LIKE 'thread_cache_size';

-- 查看 performance_schema 中的线程信息
SELECT * FROM performance_schema.threads 
WHERE TYPE = 'FOREGROUND' LIMIT 10\G

```

#### 服务层

服务层是 MySQL 的核心，负责 SQL 语句的解析、优化和执行。

**主要组件：**

  1. **SQL 解析器（Parser）** ：将 SQL 语句解析成语法树（AST）
  2. **查询优化器（Optimizer）** ：生成最优的执行计划
  3. **执行器（Executor）** ：根据执行计划调用存储引擎接口执行查询
  4. **查询缓存（Query Cache）** ：MySQL 8.0 已移除，缓存查询结果
  5. **内置函数** ：提供各种内置函数，如字符串函数、日期函数、聚合函数等



**SQL 解析器**

SQL 解析器使用 Bison（yacc 的 GNU 版本）生成，负责将 SQL 语句转换为内部的数据结构。

解析过程分为两个阶段：

  * **词法分析** ：将 SQL 语句分解为 token（关键字、标识符、操作符等）
  * **语法分析** ：根据 MySQL 语法规则，将 token 组装成语法树

```
SQL: SELECT * FROM users WHERE id = 1

词法分析后的 token:
SELECT, *, FROM, users, WHERE, id, =, 1

语法树:
        SELECT
       /      \
    columns   FROM
      |         |
      *       users
              WHERE
                |
              id = 1

``` 

**查询优化器**

查询优化器是 MySQL 中最复杂的组件之一，负责生成最优的执行计划。

优化器的工作包括：

  * **逻辑优化** ：等价变换、条件简化、子查询优化等
  * **物理优化** ：选择最优的访问路径（全表扫描、索引扫描等）
  * **代价估算** ：基于统计信息估算各种执行方案的代价

```sql
-- 创建测试数据库和表
CREATE DATABASE IF NOT EXISTS test_arch;
USE test_arch;

DROP TABLE IF EXISTS test_explain;
CREATE TABLE test_explain (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    age INT,
    city VARCHAR(50),
    INDEX idx_name(name),
    INDEX idx_age(age)
) ENGINE=InnoDB;

-- 插入测试数据
INSERT INTO test_explain VALUES
(1, 'Alice', 25, 'Beijing'),
(2, 'Bob', 30, 'Shanghai'),
(3, 'Charlie', 35, 'Guangzhou'),
(4, 'David', 28, 'Shenzhen'),
(5, 'Eve', 32, 'Hangzhou');

-- 查看执行计划
EXPLAIN SELECT * FROM test_explain WHERE id = 1;
EXPLAIN SELECT * FROM test_explain WHERE name = 'Alice';
EXPLAIN SELECT * FROM test_explain WHERE age > 25;
EXPLAIN SELECT * FROM test_explain WHERE city = 'Beijing';

-- 查看详细执行计划（JSON格式）
EXPLAIN FORMAT=JSON SELECT * FROM test_explain WHERE name = 'Alice'\G

-- 开启优化器追踪
SET optimizer_trace = 'enabled=on';
SELECT * FROM test_explain WHERE name = 'Alice';
SELECT * FROM information_schema.optimizer_trace\G
SET optimizer_trace = 'enabled=off';

```

#### 存储引擎层

### SQL执行流程

一条 SQL 语句在 MySQL 中的执行流程如下：

客户端发送SQL

连接器

解析器

预处理器

优化器

执行器

存储引擎

返回结果

**各组件职责：**

组件| 职责  
---|---  
连接器| 验证用户身份，获取权限  
解析器| 词法分析 + 语法分析，生成语法树  
预处理器| 语义检查，表/列是否存在，权限验证  
优化器| 生成执行计划，选择最优索引  
执行器| 调用存储引擎接口，执行查询  
存储引擎| 读取/写入数据  
  
以 `SELECT * FROM users WHERE id = 1` 为例：

  1. **连接器** ：客户端与 MySQL 建立连接，验证用户名密码，获取用户权限
  2. **解析器** ：将 SQL 语句解析成语法树，检查语法是否正确
  3. **预处理器** ：检查表 users 是否存在，列 id 是否存在，用户是否有查询权限
  4. **优化器** ：判断使用主键索引还是全表扫描，生成执行计划
  5. **执行器** ：根据执行计划，调用 InnoDB 引擎的接口读取数据
  6. **存储引擎** ：InnoDB 从 Buffer Pool 或磁盘读取数据，返回给执行器



### 存储引擎

MySQL 支持多种存储引擎，每种存储引擎都有其特定的使用场景。

#### InnoDB

InnoDB 是 MySQL 5.5 之后的默认存储引擎，也是目前使用最广泛的存储引擎。

**特点：**

  * 支持事务（ACID）
  * 支持行级锁
  * 支持外键约束
  * 支持 MVCC（多版本并发控制）
  * 支持崩溃恢复
  * 支持热备份



**适用场景：**

  * 需要事务支持的应用
  * 高并发读写场景
  * 数据完整性要求高的场景



#### MyISAM

MyISAM 是 MySQL 5.5 之前的默认存储引擎。

**特点：**

  * 不支持事务
  * 只支持表级锁
  * 不支持外键
  * 支持全文索引（MySQL 5.6 后 InnoDB 也支持）
  * 存储空间小，访问速度快



**适用场景：**

  * 以读为主的应用
  * 不需要事务支持的场景
  * 数据仓库、日志系统



#### Memory

Memory 存储引擎将数据存储在内存中。

**特点：**

  * 数据存储在内存，访问速度极快
  * 服务器重启后数据丢失
  * 只支持表级锁
  * 不支持 BLOB 和 TEXT 类型
  * 使用 Hash 索引（也支持 B-Tree）



**适用场景：**

  * 临时表
  * 缓存表
  * 会话数据



#### CSV

CSV 存储引擎将数据存储为 CSV（逗号分隔值）格式的文本文件。

**特点：**

  * 数据以 CSV 格式存储，可用文本编辑器直接查看和编辑
  * 不支持索引
  * 不支持 NULL 值，所有列必须定义为 NOT NULL
  * 不支持事务
  * 适合数据交换和导入导出



**适用场景：**

  * 数据导入导出的中间表
  * 与 Excel、其他系统交换数据
  * 日志数据的临时存储

```sql
-- 创建 CSV 表
CREATE TABLE csv_test (
    id INT NOT NULL,
    name VARCHAR(100) NOT NULL,
    value DECIMAL(10,2) NOT NULL
) ENGINE=CSV;

-- 数据文件会生成为 csv_test.CSV，可直接用文本编辑器打开

``` 

#### Archive

Archive 存储引擎专为存储大量历史归档数据而设计。

**特点：**

  * 只支持 INSERT 和 SELECT，不支持 UPDATE 和 DELETE
  * 使用 zlib 压缩，压缩比高达 1:10
  * 只支持自增列上的索引
  * 不支持事务
  * 写入速度快，存储空间小



**适用场景：**

  * 日志归档
  * 历史数据存储
  * 审计数据
  * 需要长期保存但很少查询的数据

```sql
-- 创建 Archive 表
CREATE TABLE archive_log (
    id INT AUTO_INCREMENT PRIMARY KEY,
    log_time DATETIME,
    log_content TEXT
) ENGINE=ARCHIVE;

``` 

#### Blackhole

Blackhole（黑洞）存储引擎会丢弃所有写入的数据，但会记录 Binlog。

**特点：**

  * 写入的数据会被丢弃，不实际存储
  * SELECT 永远返回空结果
  * 会记录 Binlog（如果开启）
  * 支持索引定义（但不实际使用）



**适用场景：**

  * **Binlog 中继** ：在主从复制架构中作为中继节点，只转发 Binlog 不存储数据
  * **性能测试** ：测试 SQL 语法和 Binlog 开销，排除存储引擎影响
  * **SQL 语法验证** ：验证 SQL 语句语法是否正确
  * **分布式复制架构** ：作为 Binlog 分发节点

```sql
-- 创建 Blackhole 表
CREATE TABLE blackhole_test (
    id INT PRIMARY KEY,
    data VARCHAR(100)
) ENGINE=BLACKHOLE;

-- 写入数据（数据会被丢弃，但 Binlog 会记录）
INSERT INTO blackhole_test VALUES (1, 'test');

-- 查询永远返回空
SELECT * FROM blackhole_test;  -- Empty set

``` 

#### Federated

Federated 存储引擎用于访问远程 MySQL 服务器上的表。

**特点：**

  * 本地不存储数据，数据存储在远程服务器
  * 通过 MySQL 协议访问远程表
  * 支持 SELECT、INSERT、UPDATE、DELETE
  * 不支持事务、索引、ALTER TABLE



**适用场景：**

  * 跨服务器数据访问
  * 数据联邦查询
  * 分布式数据整合

```sql
-- 创建 Federated 表（连接远程服务器）
CREATE TABLE federated_users (
    id INT PRIMARY KEY,
    name VARCHAR(100)
) ENGINE=FEDERATED
CONNECTION='mysql://user:pass@remote_host:3306/db/users';

``` 

**注意：** MySQL 8.0 默认禁用 Federated 引擎，需要手动启用。

#### TokuDB

TokuDB 是 Percona 开发的高性能存储引擎，基于 Fractal Tree 索引结构。

**特点：**

  * **高压缩比** ：支持多种压缩算法（zlib、lzma、quicklz），压缩比可达 10:1
  * **高写入性能** ：Fractal Tree 索引对写入优化，适合写密集场景
  * **热索引创建** ：支持在线添加索引，不阻塞读写
  * **支持事务** ：完整的 ACID 支持
  * **MVCC** ：支持多版本并发控制



**适用场景：**

  * **大数据存储** ：需要高压缩比节省存储空间
  * **写密集型应用** ：日志系统、时序数据
  * **SSD 优化** ：减少写放大，延长 SSD 寿命



**注意：** TokuDB 已于 2020 年停止维护，Percona 8.0 不再支持。如需类似功能，可考虑 MyRocks。

```sql
-- 创建 TokuDB 表（需要安装 TokuDB 插件）
CREATE TABLE tokudb_logs (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    log_time DATETIME,
    log_data TEXT
) ENGINE=TokuDB ROW_FORMAT=TOKUDB_LZMA;

``` 

#### MyRocks

MyRocks 是 Facebook 开发的基于 RocksDB 的 MySQL 存储引擎。

**特点：**

  * **高压缩比** ：基于 LSM-Tree，压缩效果优秀
  * **写优化** ：LSM-Tree 对写入友好，减少写放大
  * **SSD 友好** ：减少随机写，延长 SSD 寿命
  * **支持事务** ：完整的 ACID 支持
  * **空间效率** ：比 InnoDB 节省 50% 以上存储空间



**适用场景：**

  * **大规模数据存储** ：社交网络、消息系统
  * **写密集型应用** ：日志、监控数据
  * **SSD 存储优化** ：需要减少写放大的场景
  * **成本敏感场景** ：需要节省存储成本



**注意：** MyRocks 主要由 Percona 和 MariaDB 提供支持，官方 MySQL 不包含。

#### NDB (MySQL Cluster)

NDB 是 MySQL Cluster 的存储引擎，提供分布式、高可用的数据存储。

**特点：**

  * **分布式存储** ：数据自动分片存储在多个节点

#### 内存结构

##### BufferPool

Buffer Pool 是 InnoDB 最重要的内存组件，用于缓存数据页和索引页，减少磁盘 I/O。

**工作原理：**

当读取数据时，InnoDB 首先检查 Buffer Pool 中是否存在该数据页：

  * 如果存在（缓存命中），直接从内存读取
  * 如果不存在（缓存未命中），从磁盘读取数据页到 Buffer Pool



当修改数据时，InnoDB 首先修改 Buffer Pool 中的数据页（称为脏页），然后通过后台线程异步刷新到磁盘。

**Buffer Pool 的组成：**

Buffer Pool 由多个页（Page）组成，每个页默认 16KB。页的类型包括：

  * **数据页（Data Page）** ：存储表数据
  * **索引页（Index Page）** ：存储索引数据
  * **Undo 页（Undo Page）** ：存储 Undo Log
  * **插入缓冲页（Insert Buffer Page）** ：存储 Change Buffer
  * **自适应哈希索引页** ：存储自适应哈希索引
  * **锁信息页** ：存储锁信息



**LRU 算法：**

Buffer Pool 使用改进的 LRU（Least Recently Used）算法管理页的淘汰。

传统 LRU 的问题：

  * 全表扫描会将大量数据页加载到 Buffer Pool，可能淘汰掉热点数据



InnoDB 的改进：

  * 将 LRU 链表分为两部分：young 区（热数据）和 old 区（冷数据）
  * 新读取的页先放入 old 区头部
  * 只有在 old 区停留超过一定时间（innodb_old_blocks_time）后再次被访问，才会移动到 young 区



LRU 链表

Old 区 (3/8)

冷数据

← 头部

尾部 →

新加载的数据

Young 区 (5/8)

热数据

← 头部

尾部 →

频繁访问

##### ChangeBuffer

Change Buffer 是 Buffer Pool 的一部分，用于缓存对**非唯一二级索引** 页的修改操作。

**工作原理：**

当修改非唯一二级索引时：

  1. 如果索引页在 Buffer Pool 中，直接修改
  2. 如果索引页不在 Buffer Pool 中，将修改操作记录到 Change Buffer



当后续读取该索引页时，会将 Change Buffer 中的修改合并（merge）到索引页。

**为什么只针对非唯一二级索引？**

  * 唯一索引需要检查唯一性约束，必须读取索引页
  * 主键索引通常是聚簇索引，数据页和索引页在一起

##### AdaptiveHashIndex

自适应哈希索引（Adaptive Hash Index，AHI）是 InnoDB 根据访问模式自动建立的哈希索引。

**工作原理：**

InnoDB 监控索引的访问模式，如果发现某些索引值被频繁访问，会自动在内存中建立哈希索引，将 B+ 树的查找转换为哈希查找，时间复杂度从 O(log n) 降低到 O(1)。

**特点：**

  * 完全自动，无需人工干预
  * 只能用于等值查询，不能用于范围查询
  * 基于 Buffer Pool 中的索引页构建
  * 可能消耗 CPU 和内存资源

##### LogBuffer

Log Buffer 是 Redo Log 的内存缓冲区，用于缓存事务产生的 Redo Log。

**工作原理：**

  1. 事务修改数据时，先将 Redo Log 写入 Log Buffer
  2. 根据刷盘策略，将 Log Buffer 刷新到磁盘的 Redo Log 文件



**刷盘策略（innodb_flush_log_at_trx_commit）：**

值| 说明| 性能| 安全性  
---|---|---|---  
0| 每秒刷新一次| 最高| 最低，可能丢失1秒数据  
1| 每次事务提交都刷新| 最低| 最高，不丢失数据  
2| 每次提交写入 OS 缓存，每秒刷盘| 中等| 中等，OS 崩溃可能丢失数据

##### 表空间

表空间（Tablespace）是 InnoDB 存储数据的逻辑容器。

**表空间类型：**

  1. **系统表空间（System Tablespace）**

     * MySQL 8.0 默认将 Undo Log 存储在独立的 Undo 表空间

##### DoublewriteBuffer

Doublewrite Buffer 是 InnoDB 用于保证数据页完整性的机制。

**问题背景：**

InnoDB 的数据页大小为 16KB，而操作系统的页大小通常为 4KB。当 InnoDB 刷新一个数据页到磁盘时，需要写入 4 个操作系统页。如果在写入过程中发生宕机，可能导致数据页只写了一部分（部分写失效，Partial Page Write）。

**解决方案：**

Doublewrite Buffer 采用**两次写** 策略：

  1. 先将脏页写入 Doublewrite Buffer（顺序写）
  2. 再将脏页写入数据文件（随机写）



如果在第二步发生宕机，可以从 Doublewrite Buffer 恢复数据页。

Doublewrite 流程

① 写入 Doublewrite Buffer 顺序写

② 写入数据文件 随机写

Buffer Pool 脏页

Doublewrite Buffer 系统表空间 2MB

数据文件 .ibd

### 总结

MySQL 的体系结构是一个分层的、模块化的设计，各层各司其职：

  1. **连接层** ：负责客户端连接管理、认证授权、线程管理
  2. **服务层** ：负责 SQL 解析、优化、执行，是 MySQL 的核心
  3. **存储引擎层** ：负责数据的存储和读取，采用插件式架构
  4. **文件系统层** ：负责数据的持久化存储



InnoDB 作为 MySQL 的默认存储引擎，其体系结构包括：

**内存结构：**

  * **Buffer Pool** ：缓存数据页和索引页，是 InnoDB 最重要的内存组件
  * **Change Buffer** ：缓存对非唯一二级索引的修改
  * **Adaptive Hash Index** ：自动建立的哈希索引，加速等值查询
  * **Log Buffer** ：Redo Log 的内存缓冲区



**磁盘结构：**

  * **表空间** ：存储数据和索引的逻辑容器
  * **Redo Log** ：保证事务持久性，支持崩溃恢复
  * **Undo Log** ：支持事务回滚和 MVCC
  * **Doublewrite Buffer** ：保证数据页的完整性



理解 MySQL 的体系结构，对于数据库的性能调优、问题排查、架构设计都有非常重要的意义。在实际工作中，需要根据业务场景合理配置各个组件的参数，充分发挥 MySQL 的性能。
